# RaceIQ Decisions

Durable architecture and stack decisions. Format: constraint, alternatives considered, selected
approach, ownership/consequences.

## 2026-08-15 -- Evolve the existing repository instead of creating a new one

**Constraint**: Bryan asked for RaceIQ inside the existing `bdcrouch79/f1-race-insights`
repository, and Bryan OS's non-negotiable startup process requires determining whether RaceIQ is
an existing registered app, an existing unregistered app, or an evolution of the existing
repository before treating it as new.

**Evidence**: `f1-race-insights` is not present in `bdc-os/registry/apps.yaml` or
`registry/priorities.yaml`. The repository has one branch, 7 commits, and no evidence of a broader
engine. Its own `docs/methodology.md` explicitly said "not a full simulation or strategy engine."

**Decision**: Treat RaceIQ as an evolution of `f1-race-insights`, not a new application. Register
one new entry (`raceiq`) in `bdc-os/registry/apps.yaml` pointing at this repository rather than
creating a second repository or a duplicate registry record.

## 2026-08-15 -- Deployment: precomputed JSON artifacts, not an on-demand Python service

**Constraint**: FastF1/pandas cannot run in a standard Cloudflare Worker, and no Python-compatible
hosting service is currently authorized for RaceIQ.

**Alternatives considered**: (1) precomputed JSON artifacts committed during controlled
generation; (2) a separately hosted Python analysis API; (3) a scheduled/queued Python worker; (4)
a hybrid frontend with a live fallback call.

**Selected approach**: Option 1 for Phase 1. See `docs/ARCHITECTURE.md` for the full rationale and
the exact cache-key convention. Options 2-4 remain the upgrade path once infrastructure access is
authorized (see `docs/ROADMAP.md`).

**Consequences**: the frontend never generates a "live" analysis; every race report states its
generation timestamp; the selector can only produce a full report for races that have already been
generated and committed.

## 2026-08-15 -- No real race has been generated in this environment

**Constraint**: this build environment's egress policy denies `livetiming.formula1.com` and
`api.jolpi.ca` (verified: `curl $HTTPS_PROXY/__agentproxy/status` showed `connect_rejected`, HTTP
403 policy denials -- not a transient failure, and per the proxy's own operating rules, a policy
denial is not something to retry or route around).

**Decision**: do not fabricate a "real" analysis to fill the demo. Instead:

- Built a clearly labeled **synthetic demo fixture** (`data/fixtures/demo-race.json`, generated by
  `scripts/generate_demo_fixture.py` using invented driver names and `dataSource:
  "demo-fixture"`) to verify the full frontend interaction path end to end.
- The frontend renders a visible "Sample data" banner and sets `noindex` whenever `dataSource ===
  "demo-fixture"`.
- The homepage's secondary CTA was changed from the brief's suggested "Explore Monaco 2024" to
  "View a Sample Report," because no real Monaco 2024 (or any other) analysis has actually been
  generated and verified here.

**Consequences / next action**: the smallest manual action to complete the golden path with real
data is to run `python scripts/generate_analysis.py <year> <event>` from an environment with
network access to FastF1's data sources, then commit the resulting file under `data/generated/`.
See `docs/CURRENT_STATE.md`.

## 2026-08-15 -- Frontend styling: hand-built design tokens instead of DaisyUI

**Constraint**: Bryan OS's default stack profile (`docs/STACK.md`) specifies Tailwind CSS +
DaisyUI. The RaceIQ brief specifies an exact, premium broadcast-style palette, typography, and
visual motif set that DaisyUI's default component/theme system is not built around.

**Decision**: use Tailwind CSS directly with RaceIQ-specific design tokens
(`apps/web/tailwind.config.ts`, `app/globals.css`) instead of DaisyUI. This is a documented
exception to the Bryan OS default stack profile, scoped to this repository's frontend only.

**Ownership**: `apps/web` owns its own component styling; no DaisyUI theme is installed.

## 2026-08-15 -- Analysis engine addition, not a rewrite of `main.py`

**Constraint**: the brief requires preserving the existing Python analysis and its charts, and
explicitly forbids deleting working source until a verified replacement exists.

**Decision**: add `analysis/raceiq/` as the new, tested, callable engine and leave `main.py` and
the root `requirements.txt` untouched and working as the original lab script. `main.py` is not
imported by or required for the production RaceIQ path.

## 2026-08-15 -- Pace and degradation charts plot relative values, not absolute lap time

**Constraint**: absolute lap times in a race session typically span well under two seconds across
the field; a zero-based bar/line chart of absolute lap time compresses that spread into
visually-identical marks, which fails the "broadcast-quality, visually impressive" requirement.

**Decision**: `PaceChart` plots `gapToFastestSeconds` (0 for the pace leader) rather than absolute
average lap time; `DegradationChart` plots the single diverging `deltaSeconds` value (orange =
slower late, cyan = faster late) rather than two near-identical opening/closing bars.
`LapEvolutionChart`'s y-axis is zoomed to the actual observed lap-time band instead of starting at
zero. Absolute values, opening/closing averages, and sample sizes remain fully available in each
chart's tooltip and in the Evidence and Methodology section -- nothing shown in the tooltip data is
hidden, only the bar/line geometry changed to make the real spread legible.

## 2026-08-16 -- Headline picks require a minimum quick-lap sample

**Constraint**: the first real generated analysis (2024 Monaco Grand Prix) surfaced a real
accuracy problem. Logan Sargeant retired early with only 14 quick laps against a field high of
~50; his few clean laps before the incident happened to average faster than everyone else's full
race, so raw ranking math made him "fastest average pace" and "largest pace decline" -- correct
arithmetic, misleading headline, and the social card would have stated it as an unqualified claim
with no lap count at all ("Logan Sargeant led average race pace at 76.233s/lap").

**Decision**: `analysis/raceiq/narrative.py` now restricts the four `summary` headline picks to
drivers whose quick-lap sample is at least `MIN_HEADLINE_SAMPLE_RATIO` (0.5) of the field's
largest sample. The full, unfiltered `paceRanking`, `consistency`, and `degradation` tables are
unaffected -- every driver still appears there with their real sample size; only which driver gets
named in `summary` and the social card changes. An excluded driver is recorded in `warnings` (e.g.
"SAR had the fastest raw average pace but only 14 quick laps and was excluded from the headline
pick as an unrepresentative sample"). If every driver in a session has a short sample (e.g. a
red-flagged race), the filter falls back to the unfiltered field rather than producing no headline
at all.

**Consequences**: this changes the meaning of already-generated `summary` output, so
`ANALYSIS_VERSION` was bumped `1.0.0 -> 1.1.0`. The one real file generated under `1.0.0` (Monaco
2024) was deliberately deleted rather than left live with the known-misleading headline; it must
be regenerated under `1.1.0` before RaceIQ has real data again. See `docs/CURRENT_STATE.md`.
`apps/web/lib/raceData.ts` was also fixed to prefer the highest `analysisVersion` when a race
exists under more than one version directory, rather than returning whichever version its
directory listing happened to enumerate first.

## 2026-08-16 -- Team-color identity swatches instead of team logos

**Constraint**: Bryan asked for team logos. The original brief is explicit and non-negotiable:
*"Do not use official Formula 1 logos, team logos, copyrighted broadcast graphics, or trademarked
visual systems without verified permission"* and RaceIQ must not imply affiliation with any team.
Team logos are trademarked assets; using them on a page that states "independent, not affiliated
with any team" is the exact contradiction that clause exists to prevent.

**Decision**: use each team's real per-season color instead, sourced from FastF1's own color
mapping (`fastf1.plotting.get_team_color`, season-aware -- not a hand-typed table that would go
stale across livery/rebrand years) rather than any logo image. `analysis/raceiq/engine.py`
attaches `drivers[].teamColor` (nullable, since an unusual historical team name may not resolve).
Rendered as a small color dot (`TeamSwatch`/`DriverWithTeam` components) next to driver names on
summary cards and the evidence panel, and as the pace-bar fill color on the social card. A color is
factual, descriptive information, not a trademarked graphic -- this is the same reasoning that
already permits driver abbreviations and factual race data elsewhere in RaceIQ (see the
independence disclaimer in `docs/METHODOLOGY.md`).

**Explicitly not done**: team colors were not applied to the chart *data-series* palette
(`lib/colors.ts`) used by the pace/consistency/degradation/lap-evolution charts. Teammates share a
team color, which would make two lines or bars harder to tell apart in exactly the charts where
readability matters most; those keep the existing categorical accent palette. Team-color swatches
are an identity marker next to a driver's name, not the chart color scheme.

## 2026-08-16 -- "Largest pace decline" must not label an improvement

**Constraint**: verifying the v1.1.0 regeneration of Monaco 2024 surfaced a second, related
accuracy problem. Among the eligible (sufficient-sample) drivers, all four top-pace drivers had a
*negative* degradation delta -- every one of them was faster late in the race than early, most
likely because a red flag/safety car made the "opening" quick-lap sample the slow one. `max(...,
key=deltaSeconds)` still picks a "winner" in that situation -- the least-improved driver -- and the
old code labeled that pick "Largest Pace Decline" even though the value was negative (an
improvement, not a decline).

**Decision**: `largestPaceDeclineDriver` (and its evidence entry) is now only populated when the
picked driver's delta is actually positive. When every eligible driver improved late, RaceIQ names
no decline headline and records why in `warnings` instead of mislabeling an improvement as a
decline. `strongestLateRaceDriver` is unaffected -- "strongest closing pace" is unambiguous
regardless of sign.

**Consequences**: another meaning-of-output change, so `ANALYSIS_VERSION` bumps `1.1.0 -> 1.1.1`.
The v1.1.0 Monaco 2024 file (which had mislabeled Russell's improvement as the "largest pace
decline") was deleted the same way the v1.0.0 file was; regenerate under `1.1.1` before RaceIQ has
real data again. See `docs/CURRENT_STATE.md`.
